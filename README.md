# Логический анализатор компонентной системы

Анализ типизированных графов с произвольными идентификаторами через Python, CLI и единый Django-интерфейс. Загрузка JSON и Excel с правами, метками и требованиями; проверка доступа, мандатной политики и состояния компонентов. Анализ детерминированный: типизированные конечные факты, трёхзначная логика, точная достижимость и выбор атомарных исправлений через Z3. ML, GNN и LLM во время анализа не используются.

## Запуск

Из корня репозитория, Python 3.11 или новее:

```bash
python3 -m venv .venv-analyzer
.venv-analyzer/bin/python -m pip install -r requirements.lock.txt
.venv-analyzer/bin/python -m pytest -q
.venv-analyzer/bin/python -m analyzer demo --closed-inventory --out results/demo
```

Команда `demo` выполняет импорт → сравнение → анализ исходного и изменённого состояний → отдельный объявленный эксперимент → поиск исправления → независимую повторную проверку. `--closed-inventory` явно принимает допущение, что XLSX перечисляет все присутствующие компоненты. Без флага отсутствие строки означает `UNKNOWN`; фильтрация ПК 1 тогда остаётся неизвестной, а не доказанно утраченной.

Побайтовые копии трёх вложений находятся в [data/sources](data/sources). Оригиналы не изменялись. Разбор HTML читает только JSON из `script#data`; JavaScript не исполняется.

## Полученный результат

Импорт даёт 231 узел / 1100 рёбер HTML и 229 / 1088 XLSX. Обнаружены два отсутствующих в таблице объекта: `1:59` и `2:90`, десять оставшихся ссылок на них, 61 неоднозначная ссылка администратора и 223 асимметричных объявления. Совпадают все 1088 рёбер общих объектов. Узлы разных ПК с одинаковыми числовыми `id` остаются разными.

В [демопрофиле](examples/demo_profile.json) каждое семантическое назначение объявлено отдельно от импортированных данных. Это локальный учебный сценарий, а не установленные права реальной системы или юридическое заключение.

| Состояние | Результат 12 проверок |
|---|---|
| HTML + явный демопрофиль | 12 PASS |
| XLSX как изменённое состояние, полный перечень объектов | 11 PASS, 1 FAIL: утрачена фильтрация |
| Дополнительный объявленный эксперимент | 9 PASS, 3 FAIL: фильтрация, регистрация, запрещённый read NAS |
| Проверенное исправление | 12 PASS |

Отсутствие пароля ПК 2 не нарушает демотребование: явно разрешённая и подтверждённая альтернатива — сертификат — сохраняется. Эксперимент из [experiment_actions.json](examples/experiment_actions.json) отдельно отключает регистратор и открывает два пути к NAS; эти изменения **не извлечены из XLSX**.

В пространстве пяти объявленных действий найден минимум: восстановить фильтр, включить регистратор и закрыть обе ACL. Целевая функция — сначала число действий, затем сумма их стоимостей: `[4, 4]`. Отключение NAS отклоняется из-за потери обязательного чтения на всех четырёх ПК. Удаление защищаемых объектов и субъектов требований также отклоняется. Проверяется атомарный совместимый набор; безопасность промежуточных шагов обслуживания не заявляется.

В строгом режиме исходники подтверждают состав и нетипизированные связи. Они не задают требований, ACL, аутентификацию, покрытие защиты или криптографические алгоритмы. Ноль исполняемых требований в таком состоянии не означает безопасность. Применимость всех 324 пунктов каталога остаётся `UNKNOWN`, пока профиль не определён.

## Команды для отдельных этапов

```bash
# Источники по умолчанию независимы; отсутствие строк не объявляется удалением.
.venv-analyzer/bin/python -m analyzer import --out results/import

# Явное сравнение состояний с полным перечнем объектов в XLSX.
.venv-analyzer/bin/python -m analyzer import --as-states --closed-inventory --out results/comparison

# Строгий анализ графа и анализ сохранённой семантической модели.
.venv-analyzer/bin/python -m analyzer analyze data/sources/graf-svyazey-pk.html --out results/strict
.venv-analyzer/bin/python -m analyzer analyze results/demo/repaired_model.json --out results/recheck

# Повторить поиск по публичному CLI.
.venv-analyzer/bin/python -m analyzer repair results/demo/experiment_model.json --out results/repair.json

# Каталог со всеми исходными полями и статусами покрытия.
.venv-analyzer/bin/python -m analyzer catalog --out results/catalog

# Отдельный квантовый профиль и компактная фикстура восстановления.
.venv-analyzer/bin/python -m analyzer analyze data/sources/graf-svyazey-pk.html --profile examples/quantum_profile.json --out results/quantum
.venv-analyzer/bin/python -m analyzer analyze examples/fixtures/keyed_backup.json --out results/keyed_backup

# Воспроизвести файлы учебных допущений и фикстур.
.venv-analyzer/bin/python -m examples.build_profiles
.venv-analyzer/bin/python -m examples.build_fixtures
```

`repair` принимает `--max-candidates` и `--timeout`. Статусы поиска различают доказанный минимум в выданном каталоге, проверенный кандидат, предел поиска, ошибку модели и `NO_VALID_REPAIR_IN_ACTION_SPACE`. Последний означает исчерпание данного каталога, а не принципиальную неустранимость проблемы. `UNKNOWN`, снятие применимости и исчезновение объекта не считаются исправлением. При неизвестных предусловиях действие недопустимо.

Для входных ошибок/противоречивой модели CLI возвращает код 2. Наличие `FAIL` в корректно проанализированной модели не является ошибкой запуска: это результат анализа. Статус поиска записывается в JSON отдельно от exit code.

## Интерфейс и артефакты

```bash
.venv-analyzer/bin/python manage.py check
.venv-analyzer/bin/python manage.py runserver 127.0.0.1:8011
```

Откройте `http://127.0.0.1:8011/`: выберите файл в блоке «Импорт» и нажмите «Запустить анализ». Файл отправляется вместе с переходом на `/analysis/`, и страница показывает именно его граф; ошибка загрузки не подменяется примером. Отдельная кнопка «Открыть пример» открывает учебную модель. На странице анализатора можно **загрузить другой граф**, увидеть нарушения, запустить разрешённые исправления и сравнить состояния «до» и «после». Старый `/tests/` перенаправляет на `/analysis/`. Граф не привязан к именам или номерам ПК.

Основной вход — [типизированный JSON](docs/portable_graph.md) `component-security-graph/v1` либо Excel с листами `Nodes`, `Edges`, `Policy`, `Settings`. Образцы обоих форматов скачиваются через «Формат данных». В Excel метки разнесены по столбцам уровня и категорий; сложные поля находятся в `attributes`, общая политика — в `Settings`. Пустая ячейка означает отсутствие данных; для известного отсутствия категорий используется `[]`. Формулы не исполняются и отклоняются.

Автоматически открывается [пример FLS с двумя ПК](examples/portable/fls_clusters.json): 6 узлов, два двусторонних взаимодействия и 12 отдельных стрелок трёх уровней, 5 нарушений и 4 выполненных требования. Пять явно разрешённых действий закрывают оба обхода и опасное копирование, включают фильтр и журнал; повторная проверка даёт 9 PASS. Изменения выполняются на копии логической модели, не на реальных компьютерах. [Пример неполных меток](examples/portable/labels_unknown.json) и [граф без семантики](examples/portable/structural_only.json) демонстрируют UNKNOWN вместо ложного положительного заключения.

Физический уровень связи показан синим, синтаксический — фиолетовым, семантический — зелёным. Каждая стрелка направлена в одну сторону; явно заданное двустороннее взаимодействие раскрывается в шесть стрелок. Пунктир обозначает объявленный маршрут через средства защиты, а не неизвестность. Вкладки показывают всю систему, компоненты выбранного ПК, укрупнённые связи между ПК и три направленные матрицы. Матрицы различают `1`, `0`, `?` и отсутствие объявления (`—`), имеют страницы и выгрузку всех объявленных каналов в CSV. В Excel для трёх уровней и кластера узла предусмотрены отдельные столбцы.

Поля `interaction`, `layers`, `bidirectional`, `protection_via` и привязка операции `channel` описаны в [контракте FLS](docs/fls_graph.md). Доступ, привязанный к каналу, требует F∧L∧S совместно с прежними фактическими условиями. Закрытие доступа не стирает физическую связь. Старые связи без уровней доступны как исходные отношения; уровни им не приписываются.

Проверки строятся по явной политике, типам, меткам и требованиям узлов. Работают чтение/запись по Bell–LaPadula, опциональный строгий Biba, категории, текущая метка и допуск, контроль передачи меток, обычная политика разрешений и запретов, роли, зависимости и ранее реализованные проверяющие модули. Подробности и границы: [мандатная модель](docs/mandatory_model.md), [формат графа](docs/portable_graph.md), [сценарий для защиты проекта](docs/defense_walkthrough.md).

Структурный Excel/HTML без требований теперь показывает «Проверка безопасности не выполнена» и UNKNOWN по полноте данных. Для подтверждённого формата Excel со столбцом `Кластер` и узлами `Мандат N — Название` в кластере `Мандаты` автоматически применяется профиль потоков: рост номера означает рост конфиденциальности, исходящие связи мандатов назначают текущие метки, остальные стрелки трактуются как возможные потоки данных. Категории и исключения рассекречивания не используются. Проверяются прямые связи с двумя метками; связи без меток и неразрешённые ссылки дают агрегатный UNKNOWN. Типы пользователей, ACL, допуски и три уровня F/L/S этим профилем не выводятся. В частности, стрелку администрирования нельзя считать передачей данных без такой договорённости. Все исходные узлы и связи сохраняются, автоматическое исправление этим профилем не разрешается. В других структурных форматах обнаружение таких узлов только предлагает кнопку «Проверить мандатные потоки». Подробности: [профиль структурного графа](docs/structural_profiles.md).

При загрузке прежнего HTML/XLSX сохраняются все исходные узлы и связи. Эти форматы не содержат полных прав и требований, поэтому строгий импорт не превращает структуру в разрешённый доступ. Статусы неизвестности, ошибки модели и область проверки видны отдельно. Сообщение об успешной проверке относится только к требованиям данной модели, а не ко всем возможным уязвимостям.

Структурный Excel поддерживает лист `Конфигурации ПК` со столбцами `ПК` либо `Кластер`, `ID`, `Сущность`, `Вход`, `Выход`. В варианте `Кластер` сохраняются как ПК, так и именованные группы — например, «Общая сеть», «Администрирование», «Мандаты». Ссылки вида `ПК 2 / Пользователь 1` разрешаются явно; неоднозначные имена остаются диагностикой. Размер листа определяется по фактическим ячейкам, поэтому файлы без служебного размера листа или с устаревшим размером также читаются. Лишние заполненные столбцы и формулы по-прежнему отклоняются.

Исправления разрешаются через `repair_policy` с точными ID узлов и связей, либо явные `mutable` и `action_catalog`. Оптимизатор не меняет метки, допуски, политику, свидетельства и неизвестные факты. Новый снимок проходит повторный анализ всех требований; установленные PASS и обязательный доступ должны сохраняться. Веб-поиск ограничен 512 кандидатами и 15 секундами. Если лимит исчерпан после нахождения допустимого набора, результат помечен `VERIFIED_CANDIDATE`, без утверждения оптимальности.

API: `POST /api/analyze/` загружает JSON/HTML/XLSX; `POST /api/repair/` получает `{model}` (также как файл multipart); `POST /api/graph-example/` с `{"example":"fls"}` проверяет пример FLS тем же импортом, пустой объект сохраняет прежний пример с метками; `GET /api/graph-example/file/?example=fls&format=xlsx` выдаёт Excel-образец FLS. CSRF включён. JSON-дампы в интерфейсе не выводятся. Прежние `/api/scenario/` и `/api/test-scenarios/` сохранены для регрессий.

```bash
.venv-analyzer/bin/python -m analyzer analyze examples/portable/mixed_security.json --out results/portable
.venv-analyzer/bin/python -m analyzer repair examples/portable/mixed_security.json --out results/portable/repair.json
.venv-analyzer/bin/python -m pytest -q
```

CLI принимает переносимый граф и каноническую модель. Помимо анализа сохраняются `graph.json` и `scope.json`. Матрицы строятся для графов до 500 узлов; сам анализ не зависит от экспорта матриц. В веб-режиме приняты пределы 5000 узлов, 20000 переходов и 10000 требований; превышение диагностируется, требования не отбрасываются молча. Генерируемый `results/` исключён из Git.

Браузерная проверка необязательна для запуска: установите Playwright в отдельное окружение и запустите `scripts/check_test_ui.py --url http://127.0.0.1:8012 --chrome /путь/к/chrome` при работающем сервере. Она проверяет настоящие загрузки, исправления, ошибки и мобильный вид. `scripts/check_fls_ui.py` с теми же параметрами проверяет направления и цвета FLS, пунктир, кластеры, матрицы, CSV и загрузку образцов JSON/XLSX. `scripts/check_landing_upload.py` проверяет выбор и перетаскивание Excel на главной странице, передачу файла в анализатор и отсутствие подмены демонстрационной моделью.

Основные результаты:

- `results/demo/report.txt` — читаемый отчёт, `comparison.json` — сравнение источников, `repair.json` — поиск исправления.
- `*_model.json`, `*_analysis.json`, `*_diff.json`: состояния, объяснения и точные изменения.
- `report.json` → `states.*.graph`: все отображаемые узлы, исходные и семантические связи, доказанные нарушители и изменения; данные для графов до и после исправления.
- `*_matrices.json`: устойчивые индексы `node_key`, наблюдаемая структурная достижимость, контекстные матрицы операций/потоков `TRUE/FALSE/UNKNOWN` и `must/may`, отдельные матрицы политики. Структура сама по себе не даёт прав.
- `results/demo/metrics.json`: время каждого импорта, вывода, анализа и поиска, размеры, число проверенных наборов и ограничения. Это один измеренный запуск; обещаний ускорения нет.
- [Реестр всех правил](data/rule_registry.json), `results/demo/coverage.json` — результаты проверки покрытия, [описание покрытия](docs/catalog_coverage.md).

Версия каталога: 1.0 от 18.11.2026; реально 324 правила и 47 разделов. Для 195 пунктов сопоставлены исполняемые **фрагменты**, 54 требуют свидетельств, 39 — дополнительных данных/формализации, 36 не поддержаны целиком. Ни один импортированный текст не считается полной реализацией нормативного пункта. Применимость банковских, государственных, АСУ и криптографических профилей автоматически не включается. В предоставленных документах нет определения F/L/S; текущий контракт трёх уровней добавлен по согласованному описанию пользователя. Цвет исходного графа не определяет уровень связи или тип безопасности.

## Устройство и ограничения

[Формальная модель](docs/formal_model.md), [схема данных и примеры](docs/data_schema.md), [JSON Schema](schemas/model.schema.json).

`importers` сохраняет источники и расхождения; `profiles` привязывает явно заданную семантику; `model` проверяет конечную типизированную базу; `logic` и `engine` вычисляют значения и объяснения; `catalog` хранит формальные соответствия; `transitions` создаёт копии состояний; `repairs` выбирает действия и перепроверяет их; `export` и `cli` готовят результаты. Django — тонкий адаптер публичного API, без базы результатов и нового сервиса.

Работают проверки запрещённых/обязательных операций, обязательных функций, покрытия защиты и аутентификации, обходов, регистрации, общих зависимостей резервов, восстановления с ключами, целостности/загрузки/параметров, несовместимых ролей, согласованности изменений и криптографической защиты участка. Доступ к журналам, секретам и копиям проверяется той же явной политикой операций над соответствующими объектами.

Учебный квантовый профиль требует заданных алгоритма, функции, параметров, материалов, наблюдения, возможностей и горизонта. Он показывает пассивное раскрытие и отдельно демонстрирует отсутствие активных read/write. Это ограниченная сценарная модель: активная подделка подписей, переход к другой личности, гибридная криптографическая композиция и доказательство нормативной допустимости не реализованы. Отсутствие параметров даёт `UNKNOWN`.

Поддержан фиксированный набор предикатов и положительные зависимости AND/OR. Самоподтверждающиеся циклы остаются неизвестными. Отрицательная рекурсия и произвольные языковые выражения диагностируются как неподдерживаемая модель. Замкнутость задаётся отдельно для отношения и области, включая перечень зависимостей и альтернатив.

Кандидаты исправлений берутся из объявленных точных шаблонов по нарушениям, фактам, условиям путей и деревьям зависимостей, затем добавляются обязательные совместные действия. Новые доказательства, ACL, ключи или копии не изобретаются. Меняются только перечисленные изменяемые факты; политика, свидетельства, возможности нарушителя и UNKNOWN недоступны оптимизатору. Каждое предложение проходит полный повторный анализ поддержанного профиля; инкрементальное ограничение подграфом не используется. Комбинаторный худший случай поиска сохраняется.

Тесты включают все 20 приёмочных свойств запроса, независимую проверку достижимости алгоритмом Warshall, полный перебор небольшого каталога для проверки оптимальности, перестановки/переименование ключей, сравнение источников, сквозной CLI и Django API. Изолированные [фикстуры](examples/fixtures) не приписывают вымышленные данные реальным файлам.

Использованы официальные технические справочники: [Programming Z3](https://z3prover.github.io/papers/programmingz3.html), [оптимизация](https://microsoft.github.io/z3guide/docs/optimization/intro/), [лексикографические цели](https://microsoft.github.io/z3guide/docs/optimization/combiningobjectives/). Они служат справкой по API, не нормативным основанием правил безопасности.
