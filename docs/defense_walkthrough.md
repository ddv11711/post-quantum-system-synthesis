# Проверка модели на защите проекта

## Что демонстрируется

Программа получает конечный типизированный граф и отдельно заданную политику.
Она проверяет, выполняются ли описанные требования при фактических состояниях
компонентов и разрешениях переходов. Имена и ID произвольны. Название узла
«межсетевой экран» не доказывает защиту: нужны типизированное покрытие и данные
о состоянии механизма.

На странице анализатора `/analysis/` один процесс: загрузка → граф с объяснениями → поиск
разрешённых изменений → повторно проверенный граф. Первым открывается учебный
пример, который использует тот же импорт и тот же анализатор, что загруженный файл.

## Последовательность демонстрации

1. Нажмите «Открыть пример» на главной странице. Для своего графа сначала выберите файл и нажмите «Запустить анализ». В учебном примере FLS с ПК1 и ПК2 обнаруживаются пять нарушений:
   запрет чтения, мандатный запрет чтения вверх, копирование в менее защищённый
   архив, выключенный фильтр и выключенный журнал. Одно фактическое событие может
   нарушать несколько независимых требований: число находок не равно числу путей.
2. Нажмите на пользователя Елену. Посмотрите текущую метку `public`, категории
   и допуск `restricted/research`. Максимальный допуск не подменяет текущую метку.
   Красный пользователь и выделенные связи относятся к подтверждённому запрещённому
   доступу, который политика не скрывает перед вычислением. Цвета самих линий
   обозначают уровни, а пунктир — маршрут через защитный компонент.
3. Нажмите «Исправить уязвимости». Разрешены пять точных изменений: перекрыть два
   интерфейса и копирование, включить фильтр и регистратор. Девять требований
   теперь выполнены. Метки данных, допуск пользователя и сами требования не изменены.
4. Переключите «До»/«После»: расположение узлов сохраняется, пользователь после
   исправления перестаёт быть красным. Физические, синтаксические и семантические
   каналы остаются: закрыто право операции, а не удалена инфраструктура. Это два
   проверенных снимка модели.
5. Скачайте JSON или Excel-образец через «Формат данных», измените имена/ID с
   согласованным обновлением ссылок и загрузите. Логика останется той же.
6. Загрузите `examples/portable/labels_unknown.json`. Неизвестные категории
   приводят к UNKNOWN. Кнопка ремонта не повышает допуск и не выдумывает метку.
7. Загрузите `examples/portable/structural_only.json` либо исходный HTML.
   Схема отображается, но без политики нельзя заключить, что система безопасна.

В примере откройте вкладки «ПК1», «ПК2» и «Между ПК»: последняя показывает два
укрупнённых узла и шесть направленных стрелок между ними. «Матрицы» содержит
три уровня с направлением строка → столбец; `1` означает действующий уровень,
`0` — отключённый, `?` — неизвестный, `—` — необъявленную связь. При нескольких
каналах значения агрегируются отдельно на каждом уровне; доказательство одного
сквозного взаимодействия проверяется по согласованному каналу в анализаторе.
Вкладка и выбранная матрица сохраняются при исправлении и переключении состояния.

## На каком основании делается вывод

| Механизм | Исполняемая проверка |
|---|---|
| Обычная политика | Фактическая достижимость read/write/execute/administer сопоставляется с явно заданными запретами и обязанностями. Полнота списка разрешений для default-deny задаётся отдельно. |
| Мандатный доступ | Сравнение уровней и наборов категорий: Bell–LaPadula для конфиденциальности, отдельно включаемый строгий Biba для целостности. |
| Допуск | Текущая метка субъекта должна укладываться в заявленный допуск. |
| Копирование | Каждый объявленный перенос проверяется на допустимость метки получателя. Рассекречивание требует точного явного разрешения; оно не создаёт фактический доступ. |
| Работоспособность | Наличие, включение, исправность и обязательные/альтернативные зависимости; положительный неподтверждённый цикл не доказывает работу. |
| Защита и вход | Работоспособное покрытие объекта заданной функцией; явно описанный обход проверяется отдельно. |
| Журнал | Возможное обязательное событие должно покрываться действующим регистратором. |
| Восстановление | Доступная копия, необходимые ключи и зависимости; отдельная проверка независимости резервов. |
| Конфигурация | Сравнение фактического значения с эталоном, целостность/доверенная загрузка, явно известные и ещё не исправленные уязвимости. |
| Полномочия | Проверка заданной несовместимой комбинации ролей и согласования изменения. |
| Каналы | Заданный криптографический профиль участка; отдельный ограниченный учебный сценарий пассивной квантовой угрозы. |
| FLS | Физические, синтаксические и семантические условия одного направленного канала; привязанные операции требуют их конъюнкции вместе с фактическими правами. |

Некоторые требования создаются по полям переносимого графа автоматически. Любой
поддержанный проверяющий модуль также можно вызвать явным `requirements` вместе
с `facts`; это не требует изменения кода или привязки к исходным ПК.

## Почему нужны три значения

TRUE/FALSE/UNKNOWN описывают факты, PASS/FAIL/UNKNOWN — вывод о требовании.
Отсутствие факта не равно FALSE. Например, отсутствие записи о ключе резервной
копии не доказывает ни наличие ключа, ни невозможность восстановления.

Положительный путь подтверждает доступ. Отсутствие пути доказывает его отсутствие
лишь в явно полном контексте субъекта, операции и сценария. Для неизвестного
контекста результат остаётся UNKNOWN. Конфликтующие факты блокируют анализ как
ошибка модели.

## Как проверяется исправление

Z3 выбирает атомарный набор из конечного каталога: сначала минимизируется число
изменений, затем их стоимость. Python заново анализирует изменённую модель и
независимую копию после сериализации. Все целевые нарушения должны стать PASS;
запрещены новые FAIL, потеря прежних PASS, исчезновение требований и удаление
защищаемых объектов/источника копии. Если найден только проверенный кандидат,
интерфейс не утверждает, что он минимальный.

## Границы результата

- Анализ касается описанных фактов и области политики, а не неизвестной реальной
  инфраструктуры. Программа не подключается к ПК и не применяет исправления к ОС.
- Структура без типов, прав и требований не определяет безопасность. Неизвестное
  отношение не получает желаемое значение ради успешного отчёта.
- Мандатная модель статическая: не реализованы динамическая смена меток сессии,
  автоматическое отслеживание «загрязнения» данных и доказательство невлияния.
- Для execute/administer не придумывается автоматическая интерпретация правил
  меток read/write. Обычная политика этих операций проверяется отдельно.
- Проверяются объявленные копии и переходы. Неописанный интерфейс, скрытый канал,
  новая CVE или реальный эксплойт не обнаруживается из одного имени компонента.
- Исходный каталог содержит 324 пункта. Реестр различает формальные фрагменты,
  внешние свидетельства и неподдержанные остатки; успешный пример не подтверждает
  выполнение всего нормативного каталога.
