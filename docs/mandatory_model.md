# Конечная модель мандатного доступа

Модуль `analyzer/mandatory.py` проверяет метки произвольных узлов без привязки к номерам компьютеров или названиям компонентов. Мандатная политика и фактическая возможность операции вычисляются отдельно. Запрет политики не удаляет опасный переход и не скрывает его свидетельствующий путь.

Это исполняемый ограниченный профиль, а не утверждение о полной реализации нормативного каталога или доказательство безопасности операционной системы. Мандатное управление опирается на централизованные метки и полномочия; владелец данных не может самостоятельно понизить их классификацию. Такое разделение согласуется с [определением MAC в NIST](https://csrc.nist.gov/glossary/term/mandatory_access_control).

## Входной контракт

```json
{
  "security_policy": {
    "enabled": true,
    "confidentiality_levels": ["public", "internal", "secret"],
    "categories": ["HR", "ENG"],
    "integrity_enabled": true,
    "integrity_levels": ["untrusted", "reviewed", "trusted"],
    "integrity_categories": [],
    "declassifications": []
  },
  "nodes": {
    "operator": {
      "types": ["subject"],
      "security_label": {"level": "internal", "categories": ["HR"]},
      "clearance": {"level": "secret", "categories": ["HR", "ENG"]},
      "integrity_label": {"level": "trusted", "categories": []}
    },
    "record": {
      "types": ["data"],
      "security_label": {"level": "secret", "categories": ["HR"]},
      "integrity_label": {"level": "reviewed", "categories": []}
    }
  },
  "requirements": [
    {"id": "read-label-check", "checker": "mandatory_access", "subject": "operator", "object": "record", "operation": "read"},
    {"id": "session-clearance", "checker": "clearance", "subject": "operator", "object": "operator"}
  ]
}
```

Это фрагмент модели. Факты присутствия, реальные ACL и типизированные переходы задаются отдельно обычным API анализатора. Сами метки не создают переходов.

Порядок уровней задаётся списком **от низшего к высшему**. Имена — непустые уникальные строки. Числа, булевы значения, дубликаты и неизвестные в объявленном порядке имена диагностируются как `MODEL_ERROR`. Порядок не угадывается по алфавиту, числовому виду строки или слову «секретно».

`categories` внутри метки — явное конечное множество отсеков. `[]` означает известное отсутствие отсеков; отсутствие поля означает неизвестность. Если политика задаёт словарь `categories` / `integrity_categories`, метки должны использовать только его элементы. Если словарь не задан, имена отсеков в метках являются явно объявленными символами; сравниваются их точные множества.

`security_label` у субъекта — его **текущая метка**, у объекта — классификация данных. `clearance` — отдельный необязательный верхний предел текущей метки субъекта. Высокий допуск не повышает текущую метку автоматически. Если потолок указан неполностью, его проверка даёт `UNKNOWN`; если поле отсутствует, `mandatory_access` не выдумывает дополнительного ограничения. Отдельный `clearance` checker при отсутствующем потолке даёт `UNKNOWN`.

`enabled: false` явно исключает этот профиль (`NOT_APPLICABLE`). Отсутствующий флаг означает неизвестную применимость (`UNKNOWN`). Строгая целостность включается только через `integrity_enabled: true`.

## Решётка меток и правила

Пусть конечный список уровней (L) задаёт ранг (r(l)). Метка имеет вид (a=(l_a,C_a)), где (C_a) — множество отсеков. Доминирование определяется так:

\[
a\succeq b \iff r(l_a)\ge r(l_b)\ \land\ C_a\supseteq C_b.
\]

Даже при равном уровне метки `{HR}` и `{ENG}` несравнимы. Неполные сведения об уровне или отсеках обрабатываются трёхзначной логикой: доказанное нарушение одного условия достаточно для `FALSE`, иначе неизвестная часть сохраняет `UNKNOWN`.

Для текущих меток субъекта (s) и объекта (o) проверяются условия конфиденциальности:

\[
BLP_{read}(s,o)=C(s)\succeq C(o),\qquad
BLP_{write}(s,o)=C(o)\succeq C(s).
\]

Это выбранный статический фрагмент Bell–LaPadula: чтение вверх и запись вниз запрещены. Мы явно отделяем текущий уровень субъекта от его максимального допуска, как различаются функции уровней в [исходной работе Bell и LaPadula](https://conferences.computer.org/sp/pdfs/early/bell76.pdf). Здесь `write` означает передачу/изменение содержимого; отдельная read-modify-write операция требует обеих проверок.

При включённой строгой целостности дополнительно проверяются:

\[
Biba_{read}(s,o)=I(o)\succeq I(s),\qquad
Biba_{write}(s,o)=I(s)\succeq I(o).
\]

То есть нельзя читать сведения меньшей целостности или писать в объект большей целостности. Противоположность направлений Biba и Bell–LaPadula изложена в [отчёте FAA DOT/FAA/AR-08/35, раздел 4.1, страницы 32–33](https://www.faa.gov/sites/faa.gov/files/aircraft/air_cert/design_approvals/air_software/AR-08-35.pdf). Этот источник используется для определения математических правил, без включения авиационных требований в локальную политику проекта.

При объявленном допуске требуется (Clearance(s)\succeq C(s)). Совместная допустимость `Allowed` — AND применимых условий конфиденциальности, целостности и допуска. Для `execute` и `administer` этот модуль не подставляет семантику чтения или записи: результат мандатного условия остаётся `UNKNOWN`.

## Фактическая возможность и статус

Пусть `Actual(s,o,op,scenario,kind)` — трёхзначная достижимость **существующего** движка по реальным типизированным переходам и их условиям. Она не использует мандатную политику в качестве фильтра.

\[
Violation=Actual\land\neg Allowed,
\qquad Compliance=Allowed\lor\neg Actual.
\]

| `Allowed` | `Actual` | Результат |
|---|---|---|
| FALSE | TRUE | FAIL с реальным путём |
| FALSE | FALSE | PASS: запрещённая операция фактически исключена |
| FALSE | UNKNOWN | UNKNOWN |
| TRUE | любое | PASS по этому мандатному требованию |
| UNKNOWN | TRUE / UNKNOWN | UNKNOWN |
| UNKNOWN | FALSE | PASS: отсутствие запрещённого доступа доказано |

При неизвестной **применимости профиля** результат сохраняется `UNKNOWN` независимо от этой таблицы. `PASS` мандатной проверки не означает, что обязательная операция доступна: для этого остаётся отдельный `required_operation`.

В `result.mandatory` экспортируются `allowed`, `actual`, раздельные условия `confidentiality`, `integrity`, `clearance`, а также обе сравниваемые метки. В `witness` сохраняется реальный путь; в `evidence` — исходные метки, порядок и их происхождение; в `unknowns` — конкретные отсутствующие поля.

## Копии, потоки и рассекречивание

Для объявленного переноса `source → object` применяется `label_flow`:

```json
{"id":"copy-label", "checker":"label_flow", "subject":"operator",
 "source":"record", "object":"copy", "operation":"write",
 "kind":"flow", "scenario":"copy"}
```

Фактический путь начинается в `source`, но по всему пути сохраняются `subject`, `operation`, `kind`, `scenario`. Без исключений требуются:

\[
C(destination)\succeq C(source),\qquad
I(source)\succeq I(destination)\text{ при включённом Biba}.
\]

Проверка относится к объявленному переносу между двумя объектами. Компилятор должен создавать такую проверку **для каждого явно заданного переноса данных**, включая промежуточные копии: проверка только конечной пары не удостоверяет метки всех промежуточных хранилищ. При вручную написанном неполном наборе требований движок не утверждает проверку неназванного остатка. Автоматическое изменение меток, динамическое отслеживание загрязнения и история чтений в эту статическую модель не входят.

Необязательное исключение для конфиденциальности задаётся точным разрешением:

```json
{
  "id": "release-approved",
  "subject": "operator", "source": "record", "target": "copy",
  "operation": "write", "scenario": "copy",
  "from_label": {"level": "secret", "categories": ["HR"]},
  "to_label": {"level": "public", "categories": []},
  "authorized": "TRUE",
  "provenance": [{"kind": "declared", "file": "local-policy.json"}]
}
```

Запись помещается в `security_policy.declassifications`. Совпасть должны субъект, источник, назначение, операция, сценарий и обе полные метки. Разрешений с wildcard нет. `authorized: UNKNOWN` не подтверждает разрешение. Несовместимые решения для одного точного переноса дают `MODEL_ERROR`. Отсутствие исключений означает строгую базовую политику.

Исключение разрешает конкретное понижение конфиденциальности; оно не создаёт реальный путь, не меняет ACL, не повышает допуск, не отменяет Biba и не делает разрешённой любую запись этого субъекта. Наличие декларации в модели не удостоверяет организационный документ: его происхождение остаётся явным входом политики.

## Исправления и неполнота

`security_policy`, метки узлов, текущие уровни и допуски не являются изменяемыми предикатами. `apply_actions` допускает только перечисленные изменяемые факты фактической конфигурации. Поэтому оптимизатор не может устранить нарушение понижением метки файла, повышением допуска или добавлением исключения. Изменение фактической ACL может закрыть опасный путь; все проверки затем вычисляются повторно, включая обязательные операции.

`semantic_readiness` возвращает `UNKNOWN` для структурного графа без достаточного семантического описания. Сам граф и цвета не определяют ACL и метки.

Для частично перечисленных зависимостей компилятор может указать `incomplete_dependencies: ["component-key"]`. Даже при истинных перечисленных условиях работоспособность такого компонента остаётся `UNKNOWN`; подтверждённое ложное обязательное условие по-прежнему даёт `FALSE`.

Проверки модели и независимый конечный эталон запускаются командой:

```bash
.venv-analyzer/bin/python -m pytest tests/test_mandatory.py tests/test_engine.py -q
```

Тесты перебирают все пары трёх уровней и четырёх множеств отсеков, отдельно проверяют направления read/write, Biba, неполные метки, допуск, реальные пути, копии, точные исключения и запрет изменения политики через исправления.
