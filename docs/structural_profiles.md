# Мандаты в структурном Excel

Обычный структурный импорт строит граф. Без семантики он не определяет требования безопасности. Вместо пустого отчёта `0 из 0` интерфейс сообщает, что проверка не выполнена, и возвращает UNKNOWN по полноте данных.

Для Excel с колонками `Кластер, ID, Сущность, Вход, Выход` пользователь подтвердил, что стрелки означают передачу данных. При наличии узлов `Мандат N — Название` в кластере `Мандаты` валидный профиль `mandate-flows-v1` применяется при загрузке. Профиль не зависит от имени файла, количества ПК или ID объектов. Для других структурных форматов он предлагается отдельной кнопкой «Проверить мандатные потоки». Условия профиля видны в интерфейсе:

- Больший номер означает более высокий уровень конфиденциальности. Номера и названия уровней должны быть уникальными.
- Исходящая связь узла мандата назначает текущую метку объекту. Она не является потоком данных и не задаёт предел допуска пользователя.
- Остальные стрелки — возможные направленные передачи данных. Связи администрирования также попадают под эту трактовку; применять профиль можно только при таком смысле исходного графа.
- Категории меток не используются. Понижение конфиденциальности запрещено; исключения рассекречивания не заданы.

Компилятор проверяет каждую прямую связь, у которой оба конца получили метки. Назначение должно иметь уровень не ниже источника. Поэтому низкий уровень → высокий уровень допустим для потока: это не доказательство чтения данных высокого уровня субъектом низкого уровня. Обратная стрелка не создаётся автоматически.

Проверка использует существующий `label_flow`: происхождение назначения метки и стрелки сохраняется, запрещённый поток получает FAIL и свидетельство из двух узлов. `subject=source` в отдельном контексте ребра служит техническим обозначением источника переноса, а не утверждением, что конкретный человек совершил действие. ACL, типы субъектов, допуски, целостность и F/L/S не выводятся. Непомеченные узлы не получают уровень по умолчанию.

Связи без двух меток и неоднозначные исходные ссылки дают один UNKNOWN с количествами и причинами. Это агрегат непроверенной области, а не одна неизвестная связь. Цепочки через непомеченные посредники не проверяются как сквозные потоки. Даже PASS всех прямых проверок относится только к этой области.

Исходный граф сохраняется в `source_graph`. Профиль не объявляет полноту всех путей и не разрешает удаление связей, изменение меток или автоматический ремонт. Для проверки операций чтения/записи и исправлений нужен типизированный вход с явными операциями и разрешёнными изменениями.

Веб-запуск использует тот же `/api/analyze/`: JSON или multipart JSON-файл с `kind: "structural_profile"`, `profile: "mandate-flows-v1"` и `graph` — исходным графом. Клиент проверяет результат на том же загруженном файле, без подстановки примера. Конфликтующие назначения меток отклоняются при явном запуске; при автоматическом распознавании остаётся строгий граф с UNKNOWN и диагностикой конфликта.

Проверки реализации:

```bash
.venv-analyzer/bin/python -m pytest -q tests/test_structural_profiles.py tests/test_structural_profile_web.py tests/test_web.py tests/test_landing_upload.py
```
