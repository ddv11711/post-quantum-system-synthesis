# Направленные физические, синтаксические и семантические каналы

FLS здесь означает явно заданное пользователем разделение взаимодействия на три уровня: физическая возможность передачи, синтаксическая совместимость и семантическая интерпретация. Это дополнительный контракт проекта. В исходном каталоге правил определения FLS нет; типы старого HTML и цвета его вершин не переосмысливаются автоматически.

Канал работоспособен только при выполнении **всех трёх** условий:

\[
Channel(a,b)=Physical(a,b)\land Syntactic(a,b)\land Semantic(a,b).
\]

Вычисление трёхзначное: `TRUE`, `FALSE`, `UNKNOWN`. Отсутствующее поле — `UNKNOWN`. Доказанное `FALSE` одного необходимого уровня достаточно для `FALSE` всего канала, даже если другой уровень неизвестен.

## Переносимый формат

```json
{
  "id": "workstation-to-storage",
  "type": "interaction",
  "source": "workstation",
  "target": "storage",
  "layers": {
    "physical": true,
    "syntactic": true,
    "semantic": "UNKNOWN"
  },
  "bidirectional": true,
  "protection_via": ["gateway", "filter"]
}
```

Узлы `workstation`, `storage`, `gateway`, `filter` должны существовать в том же графе. Поля уровней принимают JSON `true`/`false`, строки `TRUE`/`FALSE`/`UNKNOWN`; `null` и отсутствующий уровень означают неизвестность. Числовые значения `0`/`1`, неизвестные названия уровней и строка вместо словаря уровней диагностируются.

Одна запись `interaction` создаёт **направленный** канал. `bidirectional: true` явно создаёт два канала с одинаковыми исходными уровнями: `workstation-to-storage` и `workstation-to-storage::reverse`. Для них получаются шесть направленных линий уровней. Если состояние сторон различается, нужно передать два самостоятельных направленных взаимодействия с разными ID и уровнями, не использовать общий флаг двунаправленности.

`protection_via` — упорядоченный маршрут через существующие промежуточные компоненты защиты. В обратном канале его порядок разворачивается. Повторяющиеся промежуточные вершины, ссылка на несуществующий узел или использование конечной вершины как промежуточной — ошибки модели. Промежуточный узел имеет явно заданный тип `component`, `function`, `channel` либо пока неизвестный тип. Имя «firewall» само по себе не используется для выбора маршрута.

Декларация физического уровня относится ко всему указанному маршруту. Ядро не придумывает недостающие физические сегменты и не извлекает такой маршрут из нетипизированных рёбер. Это утверждение входной модели со своим происхождением.

## Канал и возможность операции

Существование канала не предоставляет право читать или изменять данные. Доступ остаётся отдельным типизированным переходом:

```json
{
  "id": "read-storage",
  "type": "access",
  "source": "workstation",
  "target": "storage",
  "subject": "operator",
  "operations": ["read"],
  "allowed": true,
  "enabled": true,
  "use_acl": true,
  "channel": "workstation-to-storage"
}
```

Для такой связи одновременно требуются существование соответствующего FLS-канала, фактический gate перехода, его ACL и остальные явно заданные условия. Идентичность субъекта, операция, сценарий и вид пути сохраняются прежним движком. Синтаксическая или семантическая совместимость не заменяет аутентификацию и фактическое управление доступом.

Политика требований, включая мандатные метки, сравнивается с вычисленной фактической возможностью отдельно. Она не удаляет запрещённый путь из графа до проверки.

Указанный канал должен точно совпасть с направлением `source → target` перехода. Если запись взаимодействия двунаправленная, ссылка на её исходный ID для обратного перехода разрешается в канал `::reverse` по конечным вершинам. Односторонний канал не подходит для обратной операции. Связывание выполняется после чтения всех рёбер, поэтому порядок записей не влияет на результат.

Старые `access`/`flow`/`copy` без поля `channel` сохраняют прежнюю явно заданную семантику. Нетипизированные связи не получают FLS-уровни и не становятся доступом. Для нового взаимодействия связь с доступом задаётся явно через `channel`; наличие рядом визуально похожего канала не связывает их автоматически.

## Транспорт и защитная функция

Для маршрута через средства защиты эффективный физический уровень вычисляется так:

\[
Physical_{effective}=Physical_{declared}\land Present(source)\land Present(target)
\land\bigwedge_{p\in protection\_via}Transport(p).
\]

`Transport(p)` использует `present`, `transport_enabled`, `healthy` и текущий `failure_mode`:

| Режим | Состояние транспорта до AND с присутствием и transport_enabled |
|---|---|
| `fail_open` | TRUE |
| `fail_closed` | FALSE |
| `normal` | значение healthy |
| отсутствует / UNKNOWN | TRUE при healthy=TRUE, иначе UNKNOWN |

Административное `enabled` защитной функции **не является** физическим gate. Поэтому отключённая фильтрация может оставить транспорт действующим. Соответствие требованиям защиты по-прежнему проверяется отдельными `protection`, `authentication` и другими требованиями. Пунктирный маршрут через защиту обозначает прохождение через названный компонент, а не доказанную эффективность его защитной функции.

Синтаксический и семантический уровни остаются явными фактами взаимодействия. Код не угадывает совместимость протоколов, форматов или смысл сообщений по именам и не подменяет отсутствие свидетельств положительным значением.

## Внутренняя модель и API

Компилятор сохраняет исходные рёбра в `source_graph`. Нормализованные каналы находятся отдельно:

```json
{
  "fls_channels": [
    {
      "id": "workstation-to-storage",
      "original_channel_id": "workstation-to-storage",
      "direction": "forward",
      "source": "workstation",
      "target": "storage",
      "layers": {"physical": "TRUE", "syntactic": "TRUE", "semantic": "UNKNOWN"},
      "protection_via": ["gateway", "filter"],
      "provenance": []
    }
  ]
}
```

Публичные функции `analyzer.fls`:

- `validate_fls(model)` — ошибки структуры, ссылок, маршрута и направлений;
- `evaluate_channel(model, channel_or_id)` — один канал;
- `evaluate_channels(model)` — список каналов в устойчивом порядке ID.

Результат содержит `layers` (нормализованные декларации), `effective_layers` (с учётом состояния физического маршрута), общее `value`, `route`, `transport_conditions`, `evidence`, `unknowns`, `provenance`. Эти же данные доступны в свидетельстве перехода `witness.edges[].fls_channel`.

Рендерер может использовать три эффективных уровня как отдельные направленные цветные линии. Цвет, пунктир и положение вершин не влияют на логический вывод.

Кэш вычисления канала ограничен одним экземпляром `Engine` и одним снимком. Новый снимок заново проверяет канал и пути. Непрерывный мониторинг внешней системы, ML и инкрементальная обработка событий этим изменением не добавляются. Оптимизатор не получает свободных переменных для уровней: он по-прежнему меняет только разрешённые факты конфигурации и полностью проверяет новое состояние.

## Проверка

```bash
.venv-analyzer/bin/python -m pytest tests/test_fls.py tests/test_portable.py tests/test_engine.py -q
```

Проверяются все 27 сочетаний трёхзначных уровней, обе стороны канала, отсутствие выдуманного доступа, точное соответствие направления, неизвестные уровни, маршруты защиты, режимы отказа, сохранение старой семантики и пересчёт после изменения снимка. JSON-схемы находятся в `schemas/portable_graph.schema.json` и `schemas/model.schema.json`; исполняемая валидация не зависит от внешнего пакета проверки JSON Schema.
